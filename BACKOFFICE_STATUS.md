## Schema governance

**Regra dura:** mudanças de schema (migrations, colunas, enums, tabelas) acontecem **APENAS** neste repo via `supabase db push`. O repo do Portal nunca toca schema — Portal lê, Backoffice define.

**Convenções (Fase 1+):**
- Tabelas e colunas em pt-BR snake_case (ex: `semanas`, `pedidos_pontuais`, `janelas_entrega`)
- Timestamps com sufixo `_at` em inglês (`created_at`, `updated_at`, `cutoff_at`)
- Dates em pt-BR (`data_entrega`, `data_inicio`, `data_corte`)
- Money como `numeric`, não `_cents`
- Quantidades de ingredientes em gramas com sufixo `_g`
- `percentual_baker` decimal (0.85 = 85%)
- Enums com sufixo `_enum` (ex: `janela_status_enum`)

**Tabelas legacy (Portal-era, NÃO mexer):** `subscriptions`, `coverage_waitlist`, `coverage_whitelist`, `weekly_orders`, `capacity_waitlist`. As duas últimas são órfãs (não em `schema_migrations`). Se conceito novo encostar nelas, criar tabela nova e referenciar, não reparar legado.

**`subscriptions` — expansão permitida, contração não (registrado em 04/09/2026).** A tabela continua na lista legacy acima, mas a regra real é mais fina do que "não mexer", e vale escrever antes que alguém trave numa migration legítima: **adicionar coluna nullable a ela é rotina** e já aconteceu na 0018 (9 colunas da Frente D), na 0020 (3 colunas do eixo de pagamento) e agora na 0039/0040/0043 (`pause_reason`, `origem_aquisicao`, `forma_pagamento`). O motivo é sempre o mesmo: são atributos DA assinatura, e o campo que eles qualificam — `status`, `payment_status` — já mora aqui; tabela satélite só pra um campo obrigaria todo leitor a consultar duas fontes pro mesmo conceito. O que continua proibido é o outro lado: **dropar coluna, apertar NOT NULL ou recriar policy de escrita** pro `authenticated` (a `subscriptions_update_own` foi dropada de propósito na 0019). A migration de contract que dropa as colunas mortas já está escrita e esperando o cutover D.2-D.4 — ver Pendências.

**`app_settings` — adotada pela governança na migration 0031 (20/jul/2026).** Era órfã Portal-era; deixou de ser intocável de propósito: a 0031 (primeira migration dela) adicionou `max_subscriptions`, e futuras mudanças de flags/limites globais do gate passam por migration normal aqui. Regra que muda de propósito é rastreável; exceção documentada seria drift. As demais legacy acima continuam intocáveis.

## Como aplicar migrations (lições aprendidas)

**Setup desta máquina:**
- Sem Docker
- Sem psql/credenciais locais
- `supabase login` via personal access token (90 dias)
- Toda migration é aplicada pelo Hugo via `supabase db push` **quando** o histórico local bate com o remoto. **Exceção (lição 0019/0020):** quando o histórico local está dessincronizado da CLI, `db push` não enxerga as migrations novas como pendentes (`supabase migration list` mostra a coluna Remote em branco pra elas). Nesse caso o caminho é colar o SQL no **SQL Editor** do Supabase. As migrations 0019 e 0020 foram aplicadas assim. Consequência: `supabase migration list` não é fonte de verdade do que existe no banco quando se usa SQL Editor — confirmar o schema direto (ex: probe na REST API).

**Sequência padrão:**

```bash
cd ~/Developer/cora-backoffice
git checkout -b feat/nome-da-mudanca
# criar supabase/migrations/00XX_nome.sql
supabase migration list   # ver o que vai aplicar
supabase db push           # confirma com Y
# verificações no SQL Editor (uma por vez — Supabase SQL Editor truncates múltiplos resultados)
git add . && git commit -m "feat(schema): ..."
git push -u origin feat/nome-da-mudanca
```

**Gotchas:**
- Supabase SQL Editor só mostra o output do último SELECT quando você cola múltiplas queries. Rode uma por vez pra ver tudo.
- Se `db push` silencia e não pede confirmação, há gap entre local e remoto.
- `CHECK` constraint com subquery falha em Postgres. Use `BEFORE INSERT OR UPDATE` trigger.
- Funções/triggers reutilizáveis já existem: `set_updated_at()`, `is_admin()`. Validar nome no DDL antes de assumir.
- `subscriptions` já tem trigger `subscriptions_set_updated_at` (0001) e policy `subscriptions_select_own` (0017). A `subscriptions_update_own` foi **dropada na 0019** (segurança): escrita no client foi revogada, toda escrita é via `service_role`. Não recriar policy de write pro `authenticated`. Não duplicar ao expandir a tabela.
- Em expand-contract, CHECK do tipo `a + b = c` já é NULL-tolerant (operando NULL → expressão NULL → CHECK passa). Não morde linhas legadas até o cutover popular os valores.

  - **Sequência não é desfeita pelo sistema.** Gerar/atualizar só numera quem está sem número (novo entra no fim da onda); renumerar a onda inteira é botão separado com confirmação; ajuste fino é troca com a vizinha (duas linhas mudam, o resto da bag fica parado).
  - **Zona H** (entrega própria) fica fora da numeração e da capacidade da bag por `zonas_entrega.entra_na_onda = false`, não por código literal `'H'` no frontend — as zonas vão mudar quando a operação crescer.
  - **Entrega sem zona não some.** Cai na onda pela `regiao` do snapshot, recebe sequência e é carregada normalmente; fica marcada na tela e sai com marca tracejada na etiqueta. Pacote real não pode ficar em limbo por campo de cadastro vazio.
  - **Etiqueta validada em P&B** (obrigatório do briefing): forma com contorno preto carrega a informação, cor só acompanha. Obs ganhou clamp de 2 linhas — texto livre de bancada já chegou a 217 caracteres e estourava a etiqueta com corte silencioso.
  - **PENDENTE (Hugo):** overrides manuais do bloco 8 (quem é H, qual Lagoa é R3) → aplicar a migration → configurar `app_settings.capacidade_bag`.
  - **NÃO entregue (bloqueado neste repo):** a UI de "sugerir zona no cadastro e deixar o operador sobrescrever". Não existe tela de cadastro de assinante aqui e a 0019 revogou UPDATE de `subscriptions` pro client autenticado — precisa de endpoint `service_role` no Portal. O helper puro (`sugereZonaPorBairro`) já está pronto e testado.
- **Ordem de rota dentro da zona + símbolo dobrado (18/08, migration 0033 + código): PR aberto, migration NÃO aplicada.** Correções do primeiro uso da 0032. Detalhe no cabeçalho e na linha da 0033 acima. O que vale lembrar:
  - **Dois níveis de ordem, não um.** `bairro_zona_default.ordem` ordena os BAIRROS dentro da zona; `ordem_rota` ordena o ASSINANTE dentro do grupo. O segundo existe porque assinante de borda de bairro não tem como ser posicionado por regra de bairro.
  - **`ordem_rota` mora no cadastro, não só na tela.** A tela já não desfaz ajuste manual, mas o ajuste morre quando as entregas do ciclo seguinte são geradas. O campo é o que faz o ajuste sobreviver à semana; os dois convivem (campo = padrão, tela = exceção do dia).
  - **Sem valor = 500, o meio da faixa** (não o fim). É o que faz um número sozinho puxar (100-499) OU empurrar (501-900) sem obrigar a numerar o bairro inteiro — com "vazio por último" só dava pra puxar, e um ajuste de uma pessoa virava manutenção de lista. Gravar exatamente 500 é o mesmo que deixar em branco. Base sem nenhum override se comporta idêntico a antes. Testado em `zonas.test.ts` ("casos reais de borda de bairro"), inclusive que o override da Maria Tereza **não reordena** os outros quatro de Icaraí.
  - **`ordem_rota` não atravessa a ordem do bairro** — entra na chave DEPOIS dela. Por isso a Suzana (Lagoa lado Jardim Botânico, zona R3) **não precisa de backfill**: a ordem 2 que a Lagoa carrega da linha de R1 já a põe entre Copacabana (2) e Gávea (4), com o empate desfeito pelo nome do bairro. Se a posição dela tiver que ser independente da ordem da Lagoa em R1, isso é mudança na chave de ordenação, não um UPDATE.
  - **Recalcular é explícito.** A sequência já atribuída não é recalculada quando a ordem dos bairros muda — usar "Recalcular sequência" por onda, com confirmação. **Consequência observada em 18/08:** aplicar a 0033 não mudou nada na tela; o ciclo 34 seguiu com a ordem antiga até alguém clicar. Quem aplicar uma migration que mexe em ordem tem que lembrar do clique, senão a etiqueta sai certa de zona e errada de sequência.
  - **Símbolo dobrado sem custo:** a marca virou coluna ao lado do bloco código+nome, cuja altura já era maior que ela. Nenhum outro elemento encolheu (restrição 4 do briefing). Limite medido: bairro de até 14 caracteres cabe em uma linha do topo; 15+ quebra e custa 5,82mm — hoje o mais longo é "São Francisco" (13).
  - **Símbolo na TELA não mudou** — o briefing pediu o aumento na etiqueta, que é o que se lê a um metro na bancada.
- **Multi-entrega por ciclo: ADIADO.** Modelar N entregas como rows é o que adiciona complexidade de verdade (e `derivaEstado` assume uma entrega só). 1 entrega/ciclo com datas livres cobre teste e lançamento. **Fio amarrado:** a `janelas_entrega` (0016) já desacopla entrega/cutoff de `semanas`, e `semanas.data_entrega`/`data_corte` estão **deprecated** (ver Tech debt). Quando o módulo migrar pra `janelas_entrega`, o `D2/D1/D0` deve ancorar na data de entrega canônica de lá.
